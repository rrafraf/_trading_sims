# OG Review - 2026-08-15

## Verdict

This is now a real simulator-comparison bench, not merely a chart experiment.
The `muni` subprocess/file bridge is implemented and currently reproduces the
simple `reference_bar` result on both saved suites.

The evidence is useful, but the word `match` is currently weaker than it looks.
The comparison checks final equity and fill count, not the actual fill sequence.
The bench therefore cannot yet serve as a trading-idea lie detector without
occasionally lying itself.

## Peer bridge

OG requested independent input from the existing M55 and Vega Codex tasks.
Both replied without implementing changes.

M55 and Vega independently agree that:

- the `muni` bridge is genuinely working for target-position, next-bar-open runs;
- parity with `reference_bar` does not prove broker or execution realism;
- timestamps, fills, fees, slippage, volume, and dirty-data behavior need closer checks;
- a strict data-quality gate is the next necessary reliability change.

OG agrees, with one added blocker: comparison equality itself is under-specified.

## What is genuinely built

- Canonical OHLCV datasets and deterministic synthetic fixtures.
- Shared target-position strategy signals.
- Adapters for `reference_bar`, Backtrader, VectorBT, PyBroker, and `muni`.
- A subprocess/file contract connecting `_trading_sims` to `muni` without merging repos.
- Normalized RunResult JSON containing cash, position, equity, fills, fees, and notes.
- Experiment and harder target-position suites.
- Human-readable reports and a `muni` evidence/trace surface.
- A deterministic same-candle reproducer that records the ambiguity instead of hiding it.

## Live verification

OG reran only `reference_bar` and `muni` against the current code:

- experiment suite: 11 of 11 rows reported matching;
- hardening suite: 7 of 7 rows reported matching;
- same-candle reproducer: one `ENTRY_EXIT_SAME_CANDLE` anomaly and one
  `INTRABAR_EXIT_AMBIGUITY` were reproduced;
- Python harness modules compiled successfully.

These checks prove that the bridge executes and that current fixtures produce
the same final totals. They do not prove fill-by-fill equivalence or realism.

## Findings

### P1 - A false behavioral match can be reported as success

`tools/compare_strategy_results.py` labels a row `match` when final equity is
within tolerance and fill count is equal. It does not compare:

- final cash;
- final position;
- fill timestamp;
- source signal timestamp;
- side;
- quantity;
- price;
- fee;
- signal count;
- policy differences.

OG constructed an in-memory example where the candidate had the opposite
position and an opposite-side fill but the same final equity and fill count.
The comparator returned `status: match`.

This weakens every green parity claim. The saved result JSON already contains
the required fill details, so this can be fixed without changing the adapters.

### P1 - Dirty market data enters ordinary runs by default

`run_strategy_matrix.py` calls `validate_bars`, but validation produces notes
and execution continues. The current suites configure `muni` with
`data_quality: warn`. Duplicate timestamps, out-of-order bars, and impossible
OHLC can therefore enter a normal comparison.

`muni` already supports `data_quality: reject`, but the harness does not apply a
single strict gate before generating signals and invoking every adapter.

The gate belongs before strategy generation. Otherwise each simulator can see
or normalize corrupted input differently and create a fake engine disagreement.

### P2 - The `muni` adapter is tied to one computer by default

`benchmark_runner/adapters/muni_adapter.py` falls back to:

```text
C:\Users\Professional\Documents\muni
```

`MUNI_ROOT` can override it, but a fresh checkout on another machine silently
depends on Rafa's directory layout. The suite or environment setup should make
this dependency explicit and fail with a short setup instruction when absent.

### P2 - The project has contradictory status sources

The newer human backlog says the CLI seam, adapter, and first parity run are
done. `muni/docs/current-state.md` and `muni/docs/agent-board.json` still call
the seam the next move or a TODO.

This is not cosmetic. The documented restart ritual tells future Codex tasks to
read those stale files first, making duplicate implementation likely.

### P2 - The harness has reports but almost no first-party assertions

There is a same-candle reproducer and many generated matrix reports, but no
focused first-party unit suite asserting exact fees, slippage, timestamps,
partial fills, final state, comparator behavior, and deterministic reruns.

Reports show examples. Assertions protect contracts.

## What is not proven

- Profitable or predictive strategy edge.
- Walk-forward or out-of-sample stability.
- Stop and limit order semantics.
- Gap-through-stop behavior.
- Same-candle stop/target ordering correctness.
- Broker-specific fills, rejections, calendars, halts, or margin.
- Latency, queue position, market impact, or order-book realism.
- LEAN parity.

The current bridge proves compatibility with a deliberately simple bar model.
That is meaningful infrastructure progress, not trading proof.

## Recommended next move

Build one **truth gate** before adding strategies or UI:

1. Reject fatal market-data errors before signal generation in normal suites.
2. Compare final cash, position, signal count, and every normalized fill.
3. Add tiny exact-number tests for fees, slippage, partial volume, last-bar
   signals, short round trips, and comparator false positives.
4. Regenerate one canonical report only after these assertions pass.

After that, choose between:

- `order-intent-v1` if the goal is execution realism;
- 30m/1h/4h walk-forward runs if the goal is strategy exploration;
- replay UI if the goal is human comprehension.

Do not add another agent strategy before the judge can verify its own verdict.
